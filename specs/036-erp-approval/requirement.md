# 需求规格：大额单据审批（erp-approval）

> 进销存扩展路线（`specs/ROADMAP.md`）批次五第二项，依赖 `028`（权限与审批人）与 `035`（站内信通道）。
> 本规格**改变单据的生效时点**：金额达到阈值时，单据先落库为「待审批」，**审批通过后才产生库存与流水**——这是全项目最重的一处语义引入，见 §2 与 `design.md` §0。

## 1. 背景

现状所有单据都是**一步式、保存即生效**（`015` §5、`021` §2）：10 万采购、8 万销售的入库 / 出库与资金口径立即变动，**没有任何前置闸门**：

- 误录 / 越权开单的代价直接落到库存与应付应收上，只能事后作废补救。
- 大额业务的责任缺少「谁批准的」这一环（`029` 审计只记录「谁做的」）。
- 管理成熟的团队通常要求「超过 X 金额先审批」，系统里没有这个能力。

`ROADMAP` 把审批放在最后一批，正是因为它是「管理成熟后才需要的层」，且依赖权限（谁能审批）与通知（怎么提醒审批人）两项前置。

## 2. 目标

1. **阈值规则**：按单据类型（采购入库 / 销售出库 / 采购退货 / 销售退货）配置「审批阈值 + 是否启用」；单据金额 ≥ 阈值时触发审批。
2. **待审批单据不生效**：触发审批的单据落库为「待审批」，**不产生任何库存变动、不写库存流水、不影响成本**（资金口径同理）；审批通过时才执行生效动作。
3. **审批动作**：通过（执行生效）/ 驳回（单据作废）/ 撤回（提交人本人撤回）；**不可自审**（提交人与审批人不得为同一人）。
4. **生效失败可重试**：审批通过时若库存已不足（`40103`）等前置条件不满足，审批保持「待审批」并返回失败原因，交由审批人拒绝或稍后重试（不产生半截数据）。
5. **提醒**：提交审批时给具备 `approvals.approve` 权限的用户发站内信（`035` 通道）；审批结果通知提交人。
6. **可见性**：单据列表与详情展示「审批状态」（待审批 / 已通过 / 已驳回 / 已撤回 / 无需审批）；待审批单据禁止编辑与作废（只能审批 / 驳回 / 撤回）。
7. **前端**：新增「单据审批」页（待我审批 / 全部 + 通过 / 驳回 + 审批规则设置）；单据列表审批状态列与详情提示 + 撤回入口。

## 3. 功能点

- **F1 数据模型**：`ApprovalRules`（按单据类型的阈值与启用）+ `Approvals`（审批记录，一张单据一条）；四类单据表追加 `ApprovalStatus`（默认「无需审批」）。
- **F2 审批触发**：`Create{PurchaseOrder|SalesOrder|PurchaseReturn|SalesReturn}` 计算金额后读规则 → 命中（启用且金额 ≥ 阈值）→ 单据落库为「待审批」+ 生成审批记录 + 发站内信，**跳过生效步骤**；未命中 → 照原流程保存即生效（行为完全不变）。
- **F3 审批人与规则**：审批人 = 具备 `approvals.approve` 权限的用户；规则维护 = `approvals.rules` 权限（列表 + 保存）。
- **F4 生效动作复用**：把「单据生效」（库存增减 + 流水 + 成本 + 审计）抽为按单据类型的**共享生效组件**，由「无需审批的创建路径」与「审批通过路径」共用（避免两套生效逻辑漂移）。
- **F5 用例与接口**：`GetApprovals`（状态 / 类型 / 提交人 / 时间筛选 + 分页）/ `GetApprovalById` / `ApproveOrder` / `RejectApproval` / `WithdrawApproval` / `GetApprovalRules` / `UpdateApprovalRules`。
- **F6 前端**：`/approvals` 页（「待我审批」/「全部」两个 tab + 通过 / 驳回抽屉含审批意见 + 操作行「审批规则」抽屉）；单据列表与详情的审批状态展示与撤回入口。
- **F7 e2e 覆盖**：阈值 1000 → 开 1500 采购单 → 单据「待审批」且**库存不变** → 审批通过 → 库存增加、单据变正常；驳回 → 单据作废、库存不变；开 800 的单据直接生效；自审被拒；提交人撤回 → 单据作废、库存不变。

## 4. 验收标准

1. `cd backend && dotnet build` / `dotnet test` 通过（含规则命中 / 未命中、待审批不生效、通过生效、驳回与撤回、库存不足重试、自审拒绝、规则维护等单测）。
2. `cd frontend && npm run type-check` / `npm run lint` / `npm run build` 全绿；`npm run test:e2e` 全量通过（含新增 `approval.spec.ts` 与采购 / 销售 / 退货既有用例回归——**未配置规则时不触发审批**，既有链路零变化）。
3. 手工验证（核心语义）：
   - 采购入库阈值 1000：开 1500 → 单据「待审批」，库存查询**无变化**、无流水、无成本影响；审批通过 → 库存 +数量、流水出现「采购入库」、单据状态正常。
   - 开 800 → 直接生效（无审批记录）。
   - 驳回 1500 的单据 → 单据「已作废 / 已驳回」，库存仍无变化。
   - 提交人撤回 → 同上（不产生库存变动）。
   - 通过时若库存已被卖光（销售出库场景）→ 返回库存不足（`40103`），审批仍为「待审批」、无半截数据。
4. 自审拒绝：提交人自己审批 → `40137`；待审批单据在非待审批状态下再审批 → `40136`。
5. 站内信：提交审批后具备 `approvals.approve` 权限的用户收到「待审批」消息（点击进入审批页）；审批完成后提交人收到结果消息。
6. 口径单一：审批状态取值与文案、生效时点、自审与重试规则只在 `design.md` §0 定义一次；未命中阈值时既有单据行为**逐条不变**（既有 e2e 全绿为证）。
7. 与既有规格联动：`015` / `016` / `021` / `022` 的 `design.md` 留有「演进（erp-approval）」注记（生效时点与共享生效组件）。

## 5. 范围外（不做）

- **多级审批 / 会签 / 或签 / 条件分支**（按金额分级、按部门 / 往来单位 / 商品路由）：只有「单一阈值 → 单级审批」。
- **审批流可视化设计器**：规则只有「单据类型 + 阈值 + 启用」，在页面内维护。
- **审批代理 / 转交 / 加签**：不做。
- **超时自动通过 / 提醒升级 / 审批 SLA**：不做（`035` 只发一条「待审批」提醒）。
- **单据编辑后重新审批**：四类单据本身**不可编辑**（`015` §5），故不存在该场景；`024` 的订单编辑是否触发审批在其规格内另行决定。
- **盘点单 / 调拨单审批**：两者无业务金额（调拨无价格、盘点不产生金额），本期不纳入；如需「按数量阈值审批」另行评估。
- **审批与 OA / 钉钉 / 企业微信集成**：不做外部审批系统对接。
- **审批规则的历史版本与生效时间**：规则单值（改了即覆盖），变更留痕由 `029` 承担。
- **审批意见模板 / 附件**：只有文本审批意见（≤ 200 字符）。
- **单据金额变更后的补充审批**：不可编辑，故不存在。

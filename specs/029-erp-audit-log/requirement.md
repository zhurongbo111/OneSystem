# 需求规格：业务操作审计日志（erp-audit-log）

> 进销存扩展路线（`specs/ROADMAP.md`）批次三第五项，依赖 `028-erp-rbac`（权限点 `auditLogs.view`）。
> 只做**业务操作留痕**：登录留痕已由 `009-user-management` 的 `UserLoginLogs` 覆盖，本规格不重复。

## 1. 背景

系统目前**查不到「谁改了什么」**：

- 商品价格被谁改成 8.8？采购单被谁作废？谁把某用户的角色权限放大了？——都没有记录。
- `009` 的 `UserLoginLogs` 只回答「谁在什么时候登录过」，**不是操作留痕**；`019` 的库存流水只覆盖库存维度，其他写操作无痕。
- 权限体系（`028`）落地后，「有权限」不等于「可追溯」：一旦发生纠纷（改了价、作废了单、调了库存），必须有字段级的操作凭证。

因此需要一套**追加写、不可修改删除、与业务同事务**的操作审计日志：业务成功才有日志，日志能还原到字段级的前后值。

## 2. 目标

1. **覆盖全部写操作**：档案（商品 / 分类 / 往来单位 / 仓库 / 客户价格 / 角色 / 用户）、单据（采购 / 销售 / 退货 / 收付款 / 盘点 / 调拨的创建、作废、关闭、结算、核销）、库存调整（期初建账 / 盘点）、权限变更（角色与用户角色）。
2. **字段级留痕**：记录关键字段的**前后值**（如 `采购价 10.00 → 8.80`），而不是只记「修改了商品」。
3. **与业务同事务**：日志写入在业务用例既有的 `IUnitOfWork` 事务内；业务失败（参数错误、库存不足、状态不允许）**不产生日志**（不留噪音）。
4. **不可篡改**：日志表纯追加，无更新 / 删除接口；纠错靠新增记录（不做物理清理）。
5. **可查可追溯**：查询页（操作人 / 资源类型 / 动作 / 资源号 / 时间范围 + 服务端分页），详情抽屉展示字段级差异。
6. **敏感信息不外泄**：密码、token、密钥等敏感字段**不落审计**（字段白名单在 `design.md` §0 明确）。

## 3. 功能点

- **F1 日志表 `AuditLogs`**：字段与索引见 `design.md` §2（含资源类型 / 动作枚举、中文摘要、字段级变更 JSON）。
- **F2 写入能力**：`IAuditLogger`（Core 抽象）+ 实现（Infrastructure），配合 `AuditChangeBuilder` 生成字段级变更 JSON（只记变化项、敏感字段排除）。
- **F3 写入接入（改造既有用例）**：按 `design.md` §0 的「资源类型 × 动作」范围表逐域接入（`012`–`028` 的写路径），**每处仅追加日志、不改业务语义**。
- **F4 查询接口**：`GET /api/audit-logs`（筛选 + 分页）、`GET /api/audit-logs/{id}`（详情含结构化变更）。
- **F5 前端「操作日志」页**（`/audit-logs`，归「系统」分组）：筛选行（操作人关键词 + 资源类型 + 动作 + 资源号 + 时间范围）+ 表格 + 详情抽屉（字段级「变更前 → 变更后」表格）。
- **F6 e2e 覆盖**：改商品价格 → 日志出现该记录且详情含 `采购价 10.00 → 8.80`；作废单据 → 日志动作「作废」；业务失败（重复编码）→ 无日志；无 `auditLogs.view` 权限的用户不可见该菜单。

## 4. 验收标准

1. `cd backend && dotnet build` / `dotnet test` 通过（含 `IAuditLogger` 调用断言、字段差异生成、敏感字段排除、失败路径不写日志、事务回滚等单测）。
2. `cd frontend && npm run type-check` / `npm run lint` / `npm run build` 全绿；`npm run test:e2e` 全量通过。
3. 覆盖验证：逐条走查 `design.md` §0 的范围表，每个资源 × 动作组合均有 e2e 或单测覆盖（至少：商品改价、采购单作废、盘点提交、用户角色变更、收付款作废各一例）。
4. 字段级差异：商品编辑（改名称 + 改采购价，手机号留空）→ 日志 `changes` 仅含真正变化的两个字段，含中文标签与前后值；未变化字段不记录。
5. 敏感字段：用户重置密码 / 创建用户 → 日志**不含**任何密码字段（单测断言 `changes` 无 `password` / `passwordHash`）。
6. 不可篡改：`AuditLogs` 无更新 / 删除接口（控制器动作清单守卫断言）；日志表无 `UpdatedAt` / `UpdatedBy` 列。
7. 事务一致：库存不足（`40103`）导致的销售开单失败、重复编码（`40101`）导致的新增失败，均**不产生日志**。
8. 权限：`auditLogs.view` 控制菜单与接口；无权限用户访问 `/audit-logs` 显示 403 页、接口返回 `40300`。

## 5. 范围外（不做）

- **登录与登出日志**：`009` 的 `UserLoginLogs` 已覆盖；本规格不合并、不迁移。
- **读操作审计**（谁查看了哪条单据）：只记写操作；查看留痕属合规特例需求，另立规格。
- **审计告警 / 异常行为分析**：不做规则引擎、不做「同一人短时间大量作废」类告警（`035` 只做库存预警）。
- **日志保留策略 / 归档 / 清理**：不做过期清理与冷备归档（数据量小；将来按需加分区或归档）。
- **防篡改（哈希链 / 签名 / 只写库）**：本期靠「无改删接口 + 数据库权限」保证，不做密码学防篡改。
- **数据库级 CDC / 触发器审计**：不做（与「显式写入、摘要可读」的取舍相反）。
- **审计日志导出**：`027` 的导出能力不覆盖日志页（需单独评估，本期不做）。
- **权限点变更的历史快照对比**：本规格记变更内容，不做「任意时点的权限视图重建」。
- **跨服务的统一审计（OTel Span 级）**：已有 OpenTelemetry 追踪，不做业务语义审计的 Span 化。

# 需求规格：角色与权限体系（erp-rbac）

> 进销存扩展路线（`specs/ROADMAP.md`）P1 平台地基 第一项，落实 `specs/ROADMAP.md` §6.5「`028` 落地时统一为既有功能补齐菜单级 / 按钮级权限」。
> 本规格启用预留码 `40300`（`AGENTS.md` §4.2 的预留码转为生产码），并修正 `AGENTS.md` §4.2 的说明。

## 1. 背景

现状**没有任何权限体系**：只要登录，就可见全部菜单、可做全部操作。

- **风险**：仓管 / 业务员 / 财务都能改商品档案、作废单据、重算成本、管理用户——一次误操作即可污染库存与资金数据。
- **`40300` 一直是预留码**：`AGENTS.md` §4.2 明确「当前无角色 / 权限体系，生产路径不会返回」，前端已按「无权限」提示预留了处置方式。
- **`ROADMAP` §6.5 已定约定**：`028` 之前的新功能沿用「登录即可见」，`028` 一次性为**全部既有功能**补齐权限点（含菜单级与按钮级），前端隐藏无权限入口。
- **后续规格依赖它**：`029` 审计（谁有权做什么）、`041` 预警通知（发给谁）、`042` 审批流（谁能审批）都以角色 / 权限为前提。

## 2. 目标

1. **角色 + 权限点**：权限点由代码内置（菜单级 + 按钮级），角色在界面上维护（角色 → 权限点集合）；用户可绑定**多个角色**（权限取并集）。
2. **内置超级管理员**：内置角色 `SuperAdmin`（拥有全部权限、不可编辑 / 删除 / 取消绑定）与默认角色 `Staff`（业务权限，可编辑）；种子 admin 用户绑定 `SuperAdmin`，既有用户迁移时绑定 `Staff`。
3. **后端强制校验**：Controller 动作以 `[RequirePermission("<key>")]` 声明所需权限点，统一过滤器校验，无权限返回 `40300`（HTTP 200，与全站一致）。
4. **前端可见性**：登录即拿到权限点集合 → 侧边菜单按权限过滤（分组内子项全无权限则不展示分组）、按钮按权限隐藏（隐藏 + 后端兜底，双保险）；无权限路由显示 403 页。
5. **全部既有功能补齐**：`012`–`027` 的每个写操作与导出 / 敏感查询都登记并落地权限点（清单见 `design.md` §0）。
6. **用户与角色管理**：新增「角色权限」页（列表 / 新增 / 编辑 / 删除 + 权限勾选）；用户新增 / 编辑表单追加「角色」多选，列表追加角色列。

## 3. 功能点

- **F1 数据模型**：`Roles`（名称唯一、备注、是否内置、审计）、`RolePermissions`（角色 → 权限点 key）、`UserRoles`（用户 → 角色）；迁移时把既有用户绑定默认角色。
- **F2 权限点清单**：内置常量类 `Permissions`（`App.Core/Auth/`），key 规则 `<域>.<动作>`，清单与说明见 `design.md` §0（唯一事实源；新增功能在本表续行）。
- **F3 权限解析**：`IPermissionResolver`（按当前用户求权限点集合，单请求内缓存）；登录响应追加 `permissions`，并提供 `GET /api/users/me/permissions` 供前端刷新。
- **F4 强制校验**：`App.Api` 注册全局 `PermissionAuthorizationFilter`，读取动作上的 `[RequirePermission]` 特性校验；未标注 `[RequirePermission]` 的动作默认**拒绝**（漏标即不通过，防止新接口默认放开）——白名单仅 `[AllowAnonymous]`（登录、健康检查）与显式标注 `[RequirePermission("public")]`？不引入该特例，改用 `SkipPermissionCheck` 特性仅用于 `GET /api/users/me/permissions` 等自身接口（在 §0 表登记）。
- **F5 角色管理页**（`/roles`）：列表（名称 / 权限数 / 用户数 / 是否内置 / 创建时间 / 操作列 编辑·删除）；新增 / 编辑抽屉（名称 + 备注 + 权限勾选树）；删除（有用户绑定 → `40120`；内置角色 → `40121`）。
- **F6 用户侧改造**：用户列表追加「角色」列；新增 / 编辑抽屉追加角色多选（必填、至少一个）；`GetUserById` / 列表出参追加角色。
- **F7 前端权限控制**：`stores/auth.ts` 维护 `permissions`；`AppLayout` 菜单按权限过滤；各域按钮 `v-if="auth.hasPermission('<key>')"`；`/403` 无权限页；请求层收到 `40300` 统一 `Message.error`（同 `40000` 处置）。
- **F8 e2e 覆盖**：建角色（仅商品查看）→ 建用户绑定 → 该用户登录：菜单只剩「基础档案 → 商品管理」、无写按钮、直接访问无权限路由显示 403、直接调无权限接口返回 `40300`；超级管理员不受限。

## 4. 验收标准

1. `cd backend && dotnet build` / `dotnet test` 通过（含权限解析、过滤器、角色 CRUD、用户角色绑定、种子与迁移回填、40300 分支等单测）。
2. `cd frontend && npm run type-check` / `npm run lint` / `npm run build` 全绿；`npm run test:e2e` 全量通过。
3. 权限生效：无权限的接口调用返回 `{ code: 40300 }`（HTTP 200）；**漏标权限点的动作默认拒绝**（新增 Controller 动作若忘记标注，集成测试断言其返回 `40300`）。
4. 菜单过滤：仅商品查看权限的用户登录后，侧边菜单只剩「基础档案 → 商品管理」；「系统」分组不展示；商品页无「新增 / 编辑 / 启停」按钮（仅搜索、列表、详情）。
5. 角色管理：新建角色勾选部分权限后保存成功；重名 → `40119`；删除有用户绑定的角色 → `40120`；编辑 / 删除内置 `SuperAdmin` → `40121`。
6. 用户角色：新增用户必须选择至少一个角色（未选 → `40000`）；多角色用户权限为并集（单测与 e2e 各一例）。
7. 迁移与种子：迁移后既有用户全部绑定默认角色 `Staff`（可正常使用业务功能）；`admin` 绑定 `SuperAdmin`；重复启动种子幂等。
8. `40300` 转正：`AGENTS.md` §4.2 的「预留码」说明更新为生产码；前端按「无权限」提示（既有约定不变）。
9. 权限清单完整：`design.md` §0 清单覆盖 `012`–`027` 的全部菜单与写操作，逐条对应到 Controller 动作（集成测试遍历所有控制器动作，断言「已标注权限点」或「在白名单内」）。

## 5. 范围外（不做）

- **数据级权限（行级 / 字段级 / 数据范围）**：不做「只能看自己负责的客户」「按仓库隔离」这类行级过滤（需在查询层注入范围条件，另立规格，通常与组织模型一起做）。
- **组织 / 部门 / 岗位模型**：不做组织树、汇报关系（审批流 `042` 采用「按权限点 + 指定审批人」的简化模型）。
- **单点登录 / 外部身份（LDAP、OAuth）**：不做，仍用本地账号 + JWT。
- **权限变更审计明细**：角色与用户角色的变更由 `029-erp-audit-log` 覆盖，本规格不单独做权限变更流水。
- **权限缓存与分布式一致性**：单实例部署下按请求查库（单请求内缓存）；不引入 Redis 级缓存与多实例失效机制。
- **临时授权 / 授权到期 / 代理审批**：不做。
- **接口级细粒度（同一动作按数据量区分）**：不做。

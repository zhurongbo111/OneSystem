# 需求规格：CRM 服务工单（erp-crm-service）

> ERP 全域路线（`specs/ROADMAP.md` §4.2）**P6 外围增强**项；CRM 并入主线的**售后侧**（`ROADMAP` §1）。
> 依赖：`013`（客户）、`030`（员工 —— 负责人）。与 `043-erp-crm-presale` 同属「CRM」菜单分组。
> 范围克制：只做**服务工单登记与状态流转**；不做 SLA、知识库、满意度、工单分类树。

## 1. 背景

`043` 补上了 CRM 的**售前侧**（线索 / 商机），但**售后侧仍空白**：

- 客户反馈 / 报修 / 投诉无处登记，处理过程无留痕，"这张单谁在跟、处理到哪一步"无法回答。
- 已成交客户的服务请求与客户主数据脱节。

本规格补上 CRM 的**售后侧**：**服务工单**，与客户主数据、员工（负责人）打通，形成"售前 → 交易 → 售后"的完整客户链条。

## 2. 目标

1. **服务工单**：登记（客户 / 联系人 / 标题 / 描述 / 优先级）、状态流转（待处理 → 处理中 → 已解决 → 已关闭）、指派负责人（员工）。
2. **状态可追溯**：记录解决时间；工单留痕（不做删除）。
3. **客户 / 员工关联**：工单挂客户（`013`），负责人为员工（`030`）。
4. **权限与菜单**：权限点续行至 `028` §0.2（`tickets.*`）；菜单续行至 `025` §0.2「CRM」分组（`043` 已建）。
5. **前端**：服务工单列表 / 表单页 / 详情。
6. **e2e 覆盖**。

## 3. 功能点

- **F1 工单列表**：`GET /api/service-tickets`（按单号 / 客户关键词、状态、优先级、负责人筛选 + 分页）。
- **F2 工单登记 / 编辑**：`POST /api/service-tickets`、`PUT /api/service-tickets/{id}`（已关闭不可编辑）；单号 `SV + yyyyMMdd + 4`；金额无关。
- **F3 状态流转**：`PUT /api/service-tickets/{id}/status`（`待处理 → 处理中 → 已解决 → 已关闭`；已解决可重开为处理中；**已关闭为终态**）；置「已解决」记录解决时间。
- **F4 指派负责人**：`PUT /api/service-tickets/{id}/assign`（选员工）。
- **F5 权限与菜单**：§0 续行 `028` / `025`（「CRM」分组）。
- **F6 e2e**：建工单 → 指派 → 受理 → 解决 → 关闭；已关闭改状态 `40172`。

## 4. 验收标准

1. `cd backend && dotnet build` / `dotnet test` 通过（状态流转、终态限制、指派、解决时间等单测）。
2. `cd frontend && npm run type-check` / `npm run lint` / `npm run build` 全绿；`npm run test:e2e` 全量通过（新增 `crm-service.spec.ts`）。
3. 手工验证：
   - 建工单（客户 A、优先级「高」）→ 指派员工 → 状态推进：处理中 → 已解决（记录解决时间）→ 已关闭。
   - 已关闭工单改状态 → `40172`；已解决重开为处理中 → 成功。
   - 工单不产生库存 / 资金影响。
4. 口径单一：状态取值与允许流转、优先级取值只在 `design.md` §0 定义一次。
5. 联动：`028` §0.2 / `025` §0.2 续行（「CRM」分组 `043` 已建）。

## 5. 范围外（不做）

- **SLA / 响应时限 / 超时升级**：不做。
- **工单分类树 / 问题类型字典**：一期只有标题 + 描述。
- **知识库 / 解决方案沉淀**：不做。
- **客户满意度回访 / 评价**：不做。
- **工单附件 / 图片**：不做文件存储。
- **服务合同 / 维修配件 / 费用结算**：不做（如需与服务收入关联另行评估）。
- **工单与销售单 / 退货单的关联**：不做。
- **多渠道受理**（电话 / 邮件 / 微信 / 在线客服接入）：只做人工登记。
- **工单审批 / 派单规则**：不做。
- **工单导出 / 报表**：一期不做（如需复用 `027` 另评）。
